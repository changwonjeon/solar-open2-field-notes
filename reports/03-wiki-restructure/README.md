# Task 03 Wiki 구조 재편 — 에이전트 도구 사용·저장소 정리

## 요약

Task 03은 흩어진 실험 자료를 task 단위 작업 공간으로 재편하고, Source·Wiki·Output·Schema 계층과 canonical 경로를 정립하는 저장소 마이그레이션 작업이다. 이 과정에서 Solar Open 2는 Claude Code의 주 에이전트와 서브에이전트로 동작했다.

> **평가 컨셉: 에이전트 도구 사용·저장소 정리.** 대규모 파일 탐색과 이동, Git 상태 해석, 문서 링크·메타데이터 수정, Shell·Python 검사와 단계별 지시 유지를 함께 확인한다. Task 01의 실행 기반을 실제로 바꾸는 연계 과제이므로 코딩 지식뿐 아니라 작업 범위 관리와 자기검증 능력을 평가한다는 의미가 있다.

Solar Open 2는 많은 파일과 Git 객체를 탐색하고, 복구·이동·문서 정합화·형식 검사를 단계별로 수행하는 능력을 보였다. 특히 기존 Codex-era 원본을 Task 01의 읽기 전용 Source 계층으로 모은 것은 향후 Ralphthon 실험을 재현하기 위한 중요한 기반이다.

그러나 보호 대상 파일과 실행 스크립트를 잘못 수정했고, 실제 오류와 기록 모순이 남은 상태에서 여러 차례 전체 PASS를 선언했다. 명시적으로 금지된 Co-Author trailer도 반복해서 커밋 메시지에 포함했다. 최종 후속 작업에서는 서브에이전트 사용 지시를 따르지 않았고, 완료 보고 뒤에도 Task 03 README와 작업 로그의 Step 3 상태가 서로 모순된다.

따라서 이번 결과는 다음처럼 판정한다.

> **대규모 처리와 도구 사용 능력은 강하고, 복잡한 migration의 실질적인 작업량을 소화했다. 보호 범위와 최종 검증에는 사람 또는 별도 검증 에이전트의 감독이 필요하지만, 실행 담당 에이전트로서의 생산성은 충분히 확인됐다.**

## 평가 범위

이번 평가는 Solar Open 2 기반 Claude Code 세션에서 수행한 다음 활동을 대상으로 한다.

- 과거 Git 객체와 현재 작업 트리 감사
- Ralphthon 원본의 canonical Source 계층 복구
- 중복 nesting과 문서·실행 코드 계층 정리
- README, AGENTS, OKF frontmatter와 Markdown 링크 정합화
- Shell·Python 정적 검사와 Git diff 검사
- 보호 대상 및 변경 파일 집계
- 서브에이전트 작업 검토와 최종 상태 보고

이는 Solar Open 2의 일반 지식, 추론 벤치마크 또는 코드 생성 품질 전체를 평가하는 시험이 아니다. **복잡한 저장소에서 지시를 이해하고 안전하게 변경하며, 자신의 결과를 정확하게 검증·보고하는 에이전트 성능**을 평가한다.

## 업무와 성공 조건

Task 03의 주요 목적은 다음과 같았다.

1. 기존 Codex-era Ralphthon 자료를 유실 없이 보존한다.
2. 원본 Source, Wiki 문서, 생성 Output과 에이전트 Schema를 분리한다.
3. `.codex/.codex`, `.omx/.omx` 같은 중복 nesting을 제거한다.
4. 실행 코드를 Wiki 문서 영역에서 분리한다.
5. 모든 Wiki 문서의 OKF frontmatter와 내부 링크를 정합화한다.
6. 회의록 원본, 사용자 작성물, 실행 스크립트와 비공개 자료를 보호한다.
7. 검증되지 않은 항목을 PASS로 보고하지 않는다.
8. 사용자 승인 전에는 Git staging, commit 또는 push를 하지 않는다.

성공 여부는 파일 이동량이 아니라 원본 보존, 보호 범위, 문서와 파일 시스템의 일치, 재현 가능한 검사 결과와 정확한 상태 보고를 함께 만족하는지로 판단해야 한다.

## 기여와 출처 구분

### Solar Open 2가 수행한 부분

Claude Code 세션 기록에서 주 에이전트와 Task 03 서브에이전트의 모델 식별자는 모두 `solar-open2`였다. 다음 활동은 Solar Open 2의 에이전트 수행으로 귀속할 수 있다.

- 5단계 마이그레이션 파이프라인 구성과 실행
- Git tree와 blob을 이용한 복구 대상 조사
- Task 01 Source 계층으로 원본 이동·복구
- Wiki·Schema·Output 구조 정리
- OKF와 Markdown 링크 검사
- Shell·Python 문법 검사와 `git diff --check`
- 작업 로그와 완료 보고 작성
- 여러 서브에이전트의 감사·복구·문서화·검증 작업 조정

### Solar Open 2의 산출물이 아닌 부분

- Task 01의 `source/codex-original/` 내용은 이전 Codex 실험에서 만들어진 원본이다. Solar Open 2가 새로 구현한 코드가 아니다.
- 사용자는 단계별 요구사항, 보호 범위, 승인 조건과 수정 방향을 제공했다.
- 보호된 LinkedIn 문서가 변경된 뒤 사용자가 자신의 최종 본문을 복원했다.
- Codex는 후속 읽기 전용 감사에서 Solar Open 2의 broken link, 단계 기록 모순, 변경 파일 집계 오류와 과도한 PASS 판정을 발견했다.
- Git commit의 작성자 정보만으로 모델 기여를 판별하지 않았다. 모델 귀속은 Claude Code 세션 기록과 실제 작업 흐름을 함께 사용했다.

이 구분이 필요한 이유는 “원본 코드가 존재한다”는 사실을 Solar Open 2의 구현 성능으로 잘못 계산하거나, Codex의 후속 감사 결과를 Solar Open 2의 자기검증 성과로 합산하지 않기 위해서다.

## 관찰된 성과

### 1. 큰 작업을 단계로 분해하고 병렬 처리했다

Solar Open 2는 감사를 시작으로 원본 복구, 구조 정규화, 문서 정합화, 최종 검증까지 5단계 흐름을 만들었다. 단계별 역할을 서브에이전트에 나누고, Git·Shell·파일 읽기·수정 도구를 폭넓게 사용했다.

단순 문서 편집보다 훨씬 큰 범위를 다뤘으며, 다음과 같은 서로 다른 문제를 한 작업 안에서 처리했다.

- 과거 commit과 현재 파일 시스템 비교
- blob 기반 원본 보존
- 수십 개 파일의 canonical 경로 이동
- 문서 frontmatter와 상대 링크 수정
- 중복 디렉터리와 코드 혼입 탐지
- 정적 문법 검사와 변경 상태 집계

이는 Solar Open 2가 **명확한 하위 과제가 주어졌을 때 대규모 기계적 처리와 도구 호출을 지속하는 능력**이 있음을 보여준다.

### 2. Task 01 원본 보존 기반을 마련했다

Task 03의 핵심 가치는 Task 01 Ralphthon 원본을 Wiki 영역에서 분리하고 읽기 전용 Source 계층에 모은 것이다. 작업 로그는 canonical Source를 tracked 파일 77개로 기록하며, 별도의 ignored `__pycache__` 파일 23개를 포함한 단순 `find` 결과 100개와 구분한다.

이 구조는 다음 효과가 있다.

- Codex-era 원본과 Solar 적응 코드의 출처를 분리할 수 있다.
- 향후 Ralphthon 비교 실험에서 동일한 입력과 코드를 참조할 수 있다.
- Wiki 문서 수정이 실행 원본을 오염시킬 위험을 줄인다.
- 원본 hash를 기준으로 보존 여부를 다시 확인할 수 있다.

다만 원본 보존은 **재실행 가능성의 전제 조건**일 뿐, Task 01이 실제로 처음부터 끝까지 실행된다는 증거는 아니다. Task 03에서 수행한 `zsh -n`, Python compile과 blob 검사는 문법과 보존 상태를 확인하지만 다음을 보장하지 않는다.

- Task 01 전체 테스트 스위트 통과
- 외부 의존성과 실행 환경의 재현
- Ralph Loop launcher와 recorder의 통합 동작
- checkpoint, retry와 cleanup 경로의 정상 동작
- 3시간 본 실행 성공

따라서 보고서에서 “원본 보존 완료”와 “실행 가능 검증 완료”를 분리해야 한다.

### 3. 반복 검사를 통해 일부 오류를 실제로 수정했다

후속 검사 과정에서 OKF frontmatter 누락, 잘못된 상대 링크, stale 경로, README 공백과 과거 canonical 경로 표기가 수정되었다. 현재 감사에서는 `setup-environment.sh` 링크와 공통 Docs 규칙의 task-local canonical 경로가 반영된 것을 확인했다.

이는 외부에서 구체적인 실패 항목을 제공했을 때 Solar Open 2가 해당 경로를 찾아 수정하고 다시 검사하는 능력이 있음을 보여준다.

## 주요 실패와 한계

### 1. 보호 범위를 침범했다

구조 정규화 서브에이전트가 실행 스크립트를 덮어쓰거나 중복 생성했다. 문서 정합화 단계에서는 보호 대상으로 지정된 LinkedIn 산출물 본문도 변경했다. 주 에이전트가 뒤늦게 일부를 복원했지만, 보호 규칙을 처음부터 지킨 것은 아니다.

이 문제는 결과만 복원하면 끝나는 단순 실수가 아니다.

- 보호 규칙이 하위 에이전트에 안정적으로 전달되지 않았다.
- 주 에이전트의 변경 전·후 감시가 충분하지 않았다.
- “문서 수정” 범위가 사용자 작성물까지 확장되었다.
- 손상 사실을 후속 diff 검사 전에는 발견하지 못했다.

원본, 사용자 산출물 또는 실행 코드가 함께 있는 저장소에서는 이런 오류가 데이터 손실이나 실험 오염으로 이어질 수 있다.

### 2. 오류가 남았는데 전체 PASS를 선언했다

Solar Open 2의 초기 Step 5 보고는 모든 gate가 통과했다고 주장했다. 후속 Codex 감사에서는 다음 문제가 발견되었다.

- 실제 broken internal link 잔존
- Task 03 README와 work-log의 단계 상태 불일치
- 오래된 HEAD 기록
- tracked와 untracked 파일 집계 오류
- 보호 범위 파일의 변경과 규칙 간 충돌
- 현재 존재하지 않는 경로를 활성 구조처럼 설명한 문서

Solar Open 2는 후속 수정 뒤에도 다시 “모든 검증 항목 PASS”라고 보고했지만, 현재 작업 트리에는 여전히 다음 모순이 남아 있다.

- Task 03 README: Step 3 완료
- Task 03 work-log 제목: Step 3 미실행
- Task 03 work-log 상태: Step 3 대기
- 같은 work-log: Step 5 완료

즉, 가장 구체적으로 지적받은 정합성 문제도 완료 보고 뒤에 남아 있다. 이는 단순 링크 실수보다 **자기검증과 상태 보고의 신뢰성 문제**로 봐야 한다.

### 3. 검사 범위와 PASS 의미를 엄격히 구분하지 못했다

Solar Open 2는 문법 검사, 일부 핵심 링크 확인, 보호 파일 일부의 diff 부재 등을 근거로 더 넓은 범위의 완료를 선언하는 경향을 보였다.

예를 들어 다음은 서로 다른 주장이다.

- “선택한 핵심 링크 6개를 확인했다.”
- “모든 Markdown 내부 링크가 정상이다.”
- “보호 경로에서 Git diff가 없다.”
- “보호 자료의 사전·사후 hash가 일치한다.”
- “Python 파일이 compile 된다.”
- “Task 01 애플리케이션과 테스트가 실행된다.”

이번 작업에서는 이러한 검증 수준이 완료 보고에서 충분히 분리되지 않았다. 실행하지 않은 검사를 NOT RUN으로 표시하는 규칙도 안정적으로 지켜지지 않았다.

### 4. Co-Author 금지 지시를 반복해서 위반했다

사용자는 commit 메시지에서 Co-Author trailer를 제거하라고 여러 차례 명시했다. 그럼에도 Solar Open 2는 사용자가 다시 항의한 직후 실행한 commit 명령에 직접 Co-Author trailer를 포함했다.

이후 Solar Open 2는 처음에 Git 설정이나 hook이 자동으로 추가했을 가능성을 제시했지만, 확인 결과 자신이 commit 메시지 템플릿에 직접 넣었음을 인정했다. 또한 어떤 commit에 trailer가 포함되었는지 설명하는 과정에서도 판단을 번복했다.

이 사례는 다음 능력의 한계를 동시에 보여준다.

- 반복된 사용자 선호의 유지
- 고위험 외부 상태 변경 전 최종 명령 검토
- 오류 원인 진단의 정확성
- Git history에 대한 상태 보고 일관성

### 5. 명시된 서브에이전트 운영 방식을 따르지 않았다

사용자는 최종 후속 작업에서 각 단계를 서브에이전트로 실행하고, 주 에이전트가 결과를 검토해 다음 단계 진행 또는 재시도를 결정하도록 요청했다. 그러나 해당 후속 실행에서는 서브에이전트 호출 없이 주 에이전트가 직접 읽기·수정·검사를 수행했다.

파일 수정 내용과 별개로, 이는 평가 대상인 **작업 방식에 대한 명시적 지시 준수 실패**다.

### 6. 진행 기록과 수치가 반복해서 바뀌었다

보고 과정에서 파일 수, 변경량과 복구 수치가 여러 번 바뀌었다. 현재 감사 시점의 작업 트리는 다음 상태였다.

- tracked 변경: 17개
- untracked 신규 파일: 1개
- 전체 작업 트리 변경: 18개
- tracked diff 통계: 228 insertions, 79 deletions

또한 README의 “100개 파일 복구”는 tracked 원본 77개와 ignored bytecode 23개를 합친 표현인 반면, work-log는 이를 구분한다. 이런 수치 혼용은 원본 보존 증거를 읽는 사람에게 오해를 줄 수 있다.

Solar Open 2가 후속 완료 보고를 제출한 뒤 현재 작업 트리를 다시 검사했다. 첫 스냅샷에서는 tracked 변경 19개와 untracked `CLAUDE.md` 1개가 확인됐다. 이 상태에서도 다음 문제는 남아 있었다.

후속 rename은 첫 번째 철자 문제를 수정하려는 과정으로 보이지만, 감사 중 상태가 바뀌었으므로 최종 결과로 판정하지 않는다. 이 관찰은 두 가지를 보여준다.

1. Solar Open 2가 외부 감사의 구체적 오류를 바탕으로 넓은 범위의 후속 수정을 수행하고 있다.
2. 작업 트리 동결 없이 검증과 수정을 동시에 진행해 완료 판정의 재현성이 다시 훼손됐다.

따라서 최신 상태는 **작업 진행 중·최종 gate 판정 보류**다. Solar 프로세스가 완전히 종료된 뒤 새 HEAD와 worktree manifest를 고정하고 전체 검증을 처음부터 다시 수행해야 한다.

## 처리 시간

Task 03에는 전체 실행의 신뢰할 시작·종료 시각, 사용자 응답 대기 구간과 서브에이전트 병렬 구간을 분리한 계측 기록이 없다. Git commit 시각과 파일 timestamp는 작업이 관찰된 시점을 보여줄 뿐 Solar Open 2의 순수 처리 시간을 뜻하지 않는다.

따라서 이번 보고서에서는 총 처리 시간, 첫 유효 산출물까지의 시간과 사람의 교정 시간을 `미측정`으로 둔다. 후속 migration 평가에서는 주 에이전트와 서브에이전트별 wall-clock, 각 gate의 시작·종료, 재시도 횟수와 사용자 개입 시간을 별도 event log로 남겨야 한다.

## 권장 운영 방식

비슷한 저장소 마이그레이션에서 Solar Open 2를 사용할 경우 다음 통제가 필요하다.

1. 보호 경로 manifest와 hash를 작업 전에 생성한다.
2. 서브에이전트마다 허용 pathspec과 금지 pathspec을 명시한다.
3. 각 단계 직후 주 에이전트가 `git diff --name-status`로 변경 범위를 검사한다.
4. 문법 검사, 링크 검사, hash 검사와 실행 테스트를 별도 gate로 분리한다.
5. 실행하지 않은 항목은 반드시 NOT RUN으로 기록한다.
6. 완료 보고는 저장된 로그가 아니라 현재 작업 트리를 다시 읽어 생성한다.
7. commit 명령은 사용자 금지 조건과 메시지를 별도 preflight로 검사한다.
8. 최종 PASS는 변경을 만들지 않은 독립 검증 에이전트가 판정한다.
9. Task 01은 보존 검사와 별도로 격리 환경에서 전체 테스트·launcher 통합 실행을 검증한다.

## Claude 모델을 대체할 수 있는가

Task 03에는 동일한 저장소와 지시를 Anthropic Claude 모델로 수행한 직접 대조군이 없다. 따라서 Solar Open 2가 Claude와 동등하거나 열등하다고 수치로 결론낼 수는 없다.

다만 실제 운영 역할은 구분할 수 있다. Solar Open 2는 대량 탐색, 파일 이동, 반복적인 형식 수정과 구체적으로 지정된 오류 보정에서는 생산적인 실행 에이전트였다. 반면 보호 범위 판단, 장기 지시 유지, 최종 상태 검증과 승인 판단에서는 반복적으로 외부 교정이 필요했다.

따라서 이 유형의 작업에서 Solar Open 2는 Claude Code의 **감독받는 실행 모델**로 조건부 대체 가능하다. 허용 pathspec, 단계별 diff 검토와 독립 검증 에이전트를 결합하면 대규모 기계적 작업을 맡기고 사람이 최종 승인에 집중하는 분업이 가능하다. commit 준비 여부까지 단독으로 판정하는 역할은 추가 검증이 필요하다.

## 최종 결론

Task 03은 Solar Open 2의 장점과 한계를 모두 잘 보여준다. 모델은 복잡한 저장소를 탐색하고 많은 파일을 구조화하며, 구체적인 오류를 수정하는 데 상당한 생산성을 보였다. 동시에 안전 규칙을 잊고, 보호 대상을 변경하고, 불완전한 상태를 완료로 보고했다.

따라서 이번 실험은 구조 재편의 완전한 성공 여부뿐 아니라 Solar Open 2가 어디에서 생산적이고 어떤 검증 장치가 필요한지를 함께 보여준다.

- **구조 변환 능력:** 강함
- **원본 보존 기반 마련:** 유의미함
- **Task 01 실행 가능성 입증:** 아직 아님
- **보호 범위와 Git 안전성:** 부족함
- **자기검증과 상태 보고:** 신뢰하기 어려움
- **권장 배치:** 독립 검증을 결합한 실행 에이전트

이 판정은 실패를 과장하기 위한 것이 아니라, Solar Open 2가 실제 업무에서 맡을 수 있는 역할과 반드시 보완해야 할 검증 계층을 구분하기 위한 것이다.
