# Task 04 성능 평가 — 코딩 능력

## 요약

Task 04는 발표용 단일 화면에서 Solar Open 2와 여러 모델의 한글·영문 토큰 수 및 토큰 분할 결과를 비교하는 Streamlit 데모를 만드는 코딩 작업이다. Solar Open 2는 발표 요구를 앱 구조로 구체화하고, 비교 대상 모델을 조사해 필요한 토크나이저를 내려받아 연결했으며, UI와 검증 스크립트를 구현하고 실행 문제를 디버깅했다. 사용자는 화면 구성, 모델 범위, Hugging Face 접근과 같은 제품 결정을 담당했고, 이후 Codex가 작업물을 태스크 중심 구조로 정리하고 커밋했다.

> **평가 컨셉: 코딩 능력.** 자연어 요구를 앱 구조로 설계하고 Python·Streamlit 코드로 구현하며, 서로 다른 외부 라이브러리와 모델을 통합하고 실행 오류를 디버깅하는 전 과정을 확인한다. 단순 코드 초안이 아니라 요구에 맞는 작동 가능한 프로토타입을 완성하는 능력을 본다는 의미가 있다.

프로토타입 구현은 이 태스크의 핵심 성과다. 여러 공급자의 토크나이저를 하나의 UI에 모으고 한글과 영문 결과를 나란히 보여주는 발표 도구를 주 세션 약 91분 동안 구성했다. 서로 다른 라이브러리와 접근 조건을 조율하고 실행 오류를 수정해 실제 앱 형태로 만든 점에서 코딩·설계·디버깅 역량을 확인할 수 있다.

핵심 검증 스크립트가 일부 오계산과 비정상 출력을 성공으로 판정한 한계도 있다. GPT 계열 fallback 결과가 직접 `tiktoken`으로 계산한 값과 달랐고, Solar 토크나이저가 한글 문장 전체를 `"."` 한 토큰으로 반환한 경우도 검증을 통과했다. 이는 프로토타입 코딩 실패라기보다 전문 비교 수치를 확정하기 위한 oracle 테스트가 설계 범위에 충분히 포함되지 않았던 문제로 구분한다.

종합 평가는 다음과 같다.

| 평가 영역 | 판단 | 근거 수준 |
|---|---|---|
| 요구사항 분석과 앱 설계 | 매우 양호 | 발표 목적과 단일 화면 요구를 Streamlit 구조로 구현 |
| 프로토타입 코딩 | 매우 양호 | 다중 tokenizer·UI·검증 경로 구현 |
| 실행 오류 디버깅 | 양호 | 접근·로드·호환 문제에 반복 대응 |
| 다중 모델 조사와 연결 | 양호 | Hugging Face 모델 10종 로드 성공 기록 |
| 발표용 UI 실용성 | 부분 입증 | 구현은 확인되나 UI smoke test 없음 |
| 토큰 수 정확성 | 불량 | GPT fallback 직접 재계산과 불일치 |
| 토큰 분할 의미 정확성 | 불량 | Solar의 `"."` 단일 토큰도 성공 처리 |
| 검증 스크립트 신뢰성 | 불량 | 로드 성공을 정확성 성공으로 오인 |
| 성능·응답 지연 | 판단 불가 | latency 측정 없음 |
| Claude 대체 가능성 | 구현 범위에서 높음 | 전문 수치는 독립 검증 필요 |

따라서 이 사례에서 Solar Open 2는 **요구사항을 설계로 전환하고 실행 가능한 앱을 완성하는 코딩 파트너**로 좋은 성능을 보였다. 여러 모델 자산과 UI를 주 세션 약 91분 안에 연결하고 문제를 디버깅한 것은 의미 있는 성과다. 토큰 비교 데이터에 독립적인 정답 oracle과 의미 검사를 추가하면 구현 성과를 신뢰 가능한 도구로 발전시킬 수 있다.

## 태스크 목적과 범위

이 데모의 목적은 한 화면에서 같은 한글·영문 텍스트가 모델별로 어떻게 토큰화되는지 보여주는 것이다. 발표자가 모델마다 다음 차이를 직관적으로 비교할 수 있어야 한다.

- 한글 입력의 토큰 수
- 영문 입력의 토큰 수
- 문자 또는 부분 문자열이 나뉘는 방식
- 동일 문장에 대한 모델별 토큰 효율 차이
- Solar Open 2와 다른 모델군의 상대적 결과

이는 단순히 라이브러리가 import되는지 확인하는 작업이 아니다. 비교 수치와 분할 표현 자체가 데모의 핵심 산출물이므로, 각 토크나이저가 올바른 모델 설정으로 로드됐는지와 표시된 결과가 실제 인코딩 결과인지가 모두 중요하다.

발표용 단일 화면이라는 조건도 별도의 품질 요구를 만든다. 모델 수가 많아져도 결과를 한눈에 비교할 수 있어야 하고, 긴 토큰 배열이나 예외 메시지가 화면을 무너뜨리지 않아야 하며, 첫 실행의 모델 다운로드 지연과 반복 입력의 응답 시간을 관리해야 한다.

## 역할과 기여 범위

### Solar Open 2의 기여

기록상 Solar Open 2는 다음 작업에 관여했다.

- 비교 가능한 모델과 토크나이저 조사
- 토크나이저 다운로드 및 연결 방법 구성
- Streamlit 앱 초안 작성
- 여러 모델을 순회하는 비교 로직 구성
- 모델 로드 상태를 확인하는 검증 스크립트 초안 작성
- 발생한 실행 문제에 대한 수정 시도

이 범위는 단순 문서 작성이 아니라 외부 모델 자산, Python 라이브러리, UI와 검증 코드를 함께 다루는 구현 작업이다. 사용자 요구를 구성요소로 나누고 다양한 인터페이스를 하나의 비교 형식으로 정규화했으며, 실행 과정의 문제를 수정해 프로토타입을 완성했다는 점에서 코딩 능력을 긍정적으로 평가한다.

### 사용자의 기여

사용자는 다음과 같은 제품·운영 결정을 담당했다.

- 발표 화면의 구성과 보여줄 정보 결정
- 비교 대상 모델 범위 조정
- Hugging Face 접근 여부와 인증 관련 판단
- 구현 결과에 대한 방향 교정

따라서 최종 프로토타입은 Solar 단독 산출물이 아니라 사용자와의 공동 작업 결과다. 특히 모델 범위와 접근 조건은 앱의 실행 가능성에 직접 영향을 주므로 모델의 자율 판단 성과로만 귀속할 수 없다.

### Codex의 후속 기여

Codex는 이후 작업물을 태스크 중심 저장소 구조로 정리하고 커밋했다. 이는 Task 04의 원래 프로토타입 구현 성능과 분리해서 봐야 한다. 파일 구조화와 커밋은 보존·관리 단계의 기여이며, 토큰 계산 로직의 정확성을 입증하지 않는다.

Task 03의 저장소 재편과 Task 04의 토크나이저 데모는 서로 다른 태스크다. Task 03은 구조 변경의 정확성, 경로 정합성, 문서화와 회귀 여부로 평가하고, Task 04는 앱 구현, 비교값 정확성, UI 동작과 검증 품질로 평가한다.

## 관측 시간

확인 가능한 실행 구간은 다음과 같다.

| 구간 | 시각(UTC) | 관측 길이 | 해석 |
|---|---|---:|---|
| 주 세션 | 16:21:06–17:52:32 | 약 91분 | 조사·구현·수정이 포함된 주 작업 구간 |
| 후속 세션 | 17:51:58–18:17:51 | 약 26분 | 주 세션과 일부 겹치는 후속 작업 구간 |

두 구간은 약 34초 겹친다. 따라서 단순 합계인 약 117분을 순차적인 총 작업 시간으로 보면 안 된다. 최초 시작부터 최종 종료까지의 관측 창은 약 117분이지만, 이 안에는 사용자 응답 대기, 다운로드, 도구 실행, 중복 세션과 후속 정리 시간이 포함될 수 있다.

이 기록만으로 다음을 산출할 수는 없다.

- Solar 모델의 순수 추론 시간
- 사람이 실제로 개입한 시간
- 모델 다운로드에 사용된 시간
- 앱 코드 작성에만 사용된 시간
- 오류 수정에 사용된 순수 시간
- 동일 작업을 Claude 모델이 수행했을 때의 상대 속도

따라서 이 보고서는 시간을 **관측된 세션 창**으로만 기록하며, 순수 처리 시간이나 생산성 지표로 해석하지 않는다.

## 구현 성과

### 1. 여러 토크나이저의 단일 인터페이스화

서로 다른 토크나이저는 설치 방식, 로드 API, 인증 조건, special token 처리와 디코딩 방식이 다를 수 있다. 이들을 한 앱에서 비교하려면 모델별 예외를 흡수하고 결과를 공통 형식으로 바꿔야 한다.

검증 기록상 Hugging Face 계열 10개 모델 중 10개가 로드됐고, GPT 계열 4개 항목 중 4개가 실행 경로에 들어갔다. 이는 모델 자산을 조사하고 다중 백엔드의 최소 연결을 구성하는 능력을 보여준다. 프로토타입의 범위를 넓히고 발표 가능한 형태의 골격을 만드는 데 Solar가 실질적으로 기여했다고 볼 수 있다.

다만 “로드 성공”은 “정확한 토크나이저 결과 생성”과 동의어가 아니다. 모델 이름, revision, tokenizer class와 fallback 정책이 정확해야 하며, 출력도 알려진 정답과 대조해야 한다.

### 2. 발표용 앱 초안

Streamlit은 짧은 시간 안에 인터랙티브 비교 화면을 만들기에 적합하다. 이 태스크는 사용자가 입력한 한글과 영문 예문을 여러 모델에 적용하고 결과를 단일 화면에 배치하는 데모 형태로 구현됐다.

이는 발표 자료를 정적인 표로 미리 만드는 것보다 재사용성이 높다. 입력 문장을 현장에서 바꾸거나 새로운 모델을 추가할 수 있고, 토큰 수뿐 아니라 분할 형태도 함께 보여줄 수 있기 때문이다.

그러나 실제 브라우저에서 화면이 정상적으로 열리고 모든 모델 카드가 표시되는지 확인한 UI smoke test 기록은 없다. 다음 항목도 검증되지 않았다.

- 좁은 화면과 발표 해상도에서의 배치
- 긴 문장과 빈 입력 처리
- 모델 다운로드 중 로딩 표시
- 일부 모델 실패 시 나머지 결과 유지
- 토큰 분할 문자열의 가독성
- 캐시 적용 여부와 재실행 안정성
- 발표 환경에서의 첫 화면 표시 시간

따라서 UI는 “구현됨”으로 볼 수 있으나 “발표 환경에서 검증됨”으로 평가할 수는 없다.

## 검증 결과와 핵심 오류

### 검증 스크립트의 표면적 결과

검증 스크립트는 종료 코드 0을 반환했다. 기록된 요약값은 다음과 같다.

| 검사군 | 표면 결과 |
|---|---:|
| Hugging Face 토크나이저 | 10/10 |
| GPT 계열 | 4/4 |
| 프로세스 종료 코드 | 0 |

이 수치만 보면 모든 토크나이저가 정상 동작한 것처럼 보인다. 그러나 독립 재계산 결과, 일부 GPT 계열 값은 크게 틀렸고 Solar 출력도 의미상 비정상이었다. 즉 이 검증은 주로 “예외 없이 어떤 값이 반환됐는가”를 검사했을 뿐, “그 값이 올바른가”를 검사하지 못했다.

### GPT fallback의 UTF-8 오계산

검증 결과에는 GPT 계열의 한글·영문 토큰 수가 각각 `50/43`으로 나타났다. 하지만 같은 입력을 실제 `tiktoken` 인코딩으로 직접 계산한 결과는 다음과 같았다.

| 인코딩 | 한글 | 영문 | 검증 결과와의 관계 |
|---|---:|---:|---|
| `o200k_base` | 12 | 5 | `50/43`과 불일치 |
| `cl100k_base` | 20 | 6 | `50/43`과 불일치 |
| `gpt2` | 41 | 6 | `50/43`과 불일치 |
| 검증 스크립트 표시값 | 50 | 43 | 실제 `tiktoken` 결과가 아님 |

`50/43`은 실제 토크나이저 인코딩 대신 UTF-8 바이트 또는 부정확한 fallback 계산을 토큰 수처럼 사용했을 가능성을 보여준다. 정확한 내부 구현의 원인은 코드 수준에서 다시 확인해야 하지만, 최소한 이 값이 위 세 `tiktoken` 기준 중 어느 것과도 일치하지 않는다는 사실은 명확하다.

이 오류는 데모의 결론을 직접 왜곡할 수 있다. 예를 들어 한글에 유리한 모델과 불리한 모델의 순위, 한글 대비 영문 토큰 효율, 비용 추정이 모두 잘못될 수 있다. 따라서 fallback이 작동했다는 사실을 정상적인 모델 결과로 표시해서는 안 된다.

안전한 처리 방식은 다음 중 하나다.

- 실제 대상 모델에 대응하는 공식 인코딩을 사용한다.
- 대응 인코딩을 결정할 수 없으면 결과를 `지원되지 않음`으로 표시한다.
- fallback 결과는 모델 토큰 수와 분리해 `UTF-8 byte estimate`처럼 명시한다.
- 앱 시작 시 알려진 fixture로 인코더를 자체 검사한다.

### Solar 토크나이저의 의미상 비정상 출력

Solar 토크나이저는 한글 문장을 `"."` 하나의 토큰으로 반환했지만 검증은 이를 성공으로 판정했다. 일반적인 한글 문장 전체가 마침표 한 토큰으로 축약되는 결과는 정상적인 토큰 분할로 보기 어렵다.

이 현상은 다음과 같은 가능성을 점검해야 한다.

- 입력 문자열 대신 잘못된 필드가 토크나이저에 전달됨
- 토큰 ID를 문자열로 복원하는 과정의 오류
- special token 또는 unknown token 처리 오류
- 모델과 맞지 않는 tokenizer revision 사용
- 결과 배열의 일부만 표시
- 디코딩 로직에서 `"."`로 치환

현재 증거만으로 정확한 원인을 하나로 단정할 수는 없다. 그러나 검증 스크립트가 이 결과를 성공으로 처리했다는 점은 확실한 결함이다. 검증은 단순히 결과가 비어 있지 않은지만 볼 것이 아니라, 입력 정보가 합리적으로 보존되고 분할 결과를 다시 결합했을 때 원문과 일치하는지를 확인해야 한다.

## 왜 검증이 실패했는가

이 태스크의 핵심 문제는 구현 실패보다 **검증 목표의 정의 부족**에 가깝다. 현재의 `10/10`, `4/4`, 종료 코드 0은 다음만 입증한다.

- 코드가 대상 항목을 순회했다.
- 일부 로드 또는 fallback 경로가 예외 없이 값을 반환했다.
- 스크립트가 자체적으로 실패 조건으로 정의한 예외가 없었다.

반면 다음은 입증하지 못한다.

- 실제 대상 모델의 올바른 토크나이저가 로드됨
- 한글·영문 토큰 수가 정답과 일치함
- 표시된 토큰 조각이 실제 인코딩과 일치함
- encode/decode round-trip이 원문을 보존함
- fallback 값이 모델 토큰 수와 의미적으로 동등함
- 비정상적으로 작은 결과가 차단됨

검증 성공률은 검사 항목의 품질에 의존한다. 잘못된 값을 실패로 분류하지 않는 테스트에서 100% 통과는 정확성의 증거가 아니다.

## 권장 독립 oracle 테스트

Claude 또는 다른 코딩 모델로 이 구현을 대체하거나 유지보수하려면 생성 모델과 독립된 정답 검사를 둬야 한다. 최소 검증 기준은 다음과 같다.

### 1. 고정 fixture

한글, 영문, 혼합문, 숫자, 이모지, 공백과 문장부호를 포함한 짧은 입력 세트를 고정한다. 각 입력에 대해 공식 토크나이저 또는 신뢰할 수 있는 직접 실행으로 정답 토큰 ID와 개수를 기록한다.

### 2. 정확한 개수 대조

지원되는 각 모델은 예상 토큰 수와 실제 결과를 완전 일치로 비교한다. 허용 범위를 두는 대신 tokenizer revision과 설정을 고정해야 한다.

GPT 계열에는 적어도 이번 독립 재계산값인 다음 항목을 회귀 fixture로 넣을 수 있다.

- `o200k_base`: 한글 12, 영문 5
- `cl100k_base`: 한글 20, 영문 6
- `gpt2`: 한글 41, 영문 6

단, 위 값은 이번 평가에 사용된 동일 문장이 유지될 때만 유효하다. fixture에는 입력 원문, 라이브러리 버전과 인코딩 이름을 함께 고정해야 한다.

### 3. round-trip 검사

토큰 ID를 다시 decode한 문자열이 입력과 일치하는지 확인한다. tokenizer 특성상 정규화가 발생한다면 허용 가능한 정규화 규칙을 명시해야 한다. 단순히 토큰 배열 길이가 1 이상인지는 충분하지 않다.

### 4. 의미적 sanity check

다음 조건은 경고 또는 실패로 처리한다.

- 여러 글자의 일반 문장이 문장부호 하나로만 표시됨
- 빈 입력이 아닌데 토큰 수가 0
- 토큰 조각을 결합해도 원문의 대부분을 복원할 수 없음
- 서로 다른 인코딩이 모든 입력에서 동일한 byte count만 반환
- 공식 결과 대신 fallback을 사용했는데 화면에서 구분되지 않음

### 5. provenance 검사

결과마다 다음 정보를 함께 보존한다.

- 모델과 tokenizer 식별자
- revision 또는 commit hash
- 라이브러리 이름과 버전
- 로드 성공 여부
- 공식 인코더 또는 fallback 여부
- 인증이 필요한 모델의 접근 상태
- 계산 오류와 표시 오류의 구분

### 6. UI와 성능 smoke test

앱 프로세스가 뜨는 것뿐 아니라 브라우저 또는 Streamlit 테스트 도구로 핵심 요소를 확인해야 한다.

- 기본 한글·영문 입력 표시
- 모델별 결과 카드 수
- 오류 모델의 격리 표시
- 결과 갱신
- 긴 결과 접기 또는 스크롤
- 첫 로드와 캐시 후 재실행 latency

발표용 도구라면 콜드 스타트, 입력 변경 후 갱신, 전체 모델 완료까지의 시간을 별도로 측정해야 한다.

## 세부 평가

### 1. 요구사항 이해

한글과 영문을 여러 모델에서 비교하고 한 화면에 표시한다는 핵심 목적은 구현 방향에 반영됐다. 모델 조사부터 다운로드, 앱과 검증 스크립트까지 필요한 구성요소도 대체로 식별했다. 이 영역은 양호하다.

다만 요구사항의 중심을 “여러 모델이 실행되는 것”으로만 해석하고 “비교값이 정확해야 하는 것”을 독립된 완료 조건으로 충분히 강화하지 못했다. 데이터 시각화 도구에서는 계산값의 정확성이 UI 구현보다 우선한다.

### 2. 환경 적응과 도구 사용

Hugging Face 토크나이저 10종과 GPT 계열 경로를 한 프로젝트에서 다룬 것은 환경 적응과 도구 사용 능력의 긍정적 증거다. 인증과 다운로드가 필요한 자산을 다루고, Streamlit UI와 검증 경로를 함께 만든 점도 실용적이다.

그러나 정상 경로를 확보하지 못했을 때 부정확한 fallback을 정상 결과로 승격한 것은 중요한 약점이다. 외부 접근 실패나 미지원 모델은 명시적 오류 상태로 남기는 편이 잘못된 비교값을 제공하는 것보다 안전하다.

### 3. 자기검증

자기검증은 이 태스크에서 가장 낮은 평가를 받는다. 종료 코드와 로드 개수는 확인했지만, 알려진 정답과의 비교, round-trip, 비정상 출력 탐지와 UI smoke test가 없었다.

특히 두 오류가 동시에 통과했다는 점이 중요하다.

- GPT 계열 `50/43` 오계산
- Solar 한글 문장의 `"."` 단일 토큰 출력

이는 개별 edge case 하나를 놓친 수준이 아니라 검증 설계가 핵심 정확성을 측정하지 못했다는 뜻이다.

### 4. 결과 보고의 신뢰성

`exit 0`, `10/10`, `4/4`는 기술적으로 해당 스크립트의 통과 결과지만, 독자가 이를 모델 결과의 정확성으로 이해할 가능성이 높다. 보고에는 반드시 “로드·실행 경로 통과”와 “토큰화 정답 검증”을 분리해 써야 한다.

향후 완료 보고는 다음 네 상태를 구분하는 것이 좋다.

- 로드 성공
- 인코딩 실행 성공
- oracle 정확성 통과
- UI 표시 검증 통과

이 네 단계가 모두 통과하지 않았다면 전체 성공으로 요약해서는 안 된다.

## 한계

이 평가에는 다음 제한이 있다.

- 동일 조건에서 Claude 모델이 구현한 대조군이 없다.
- 반복 실행이 없어 구현 안정성을 비교할 수 없다.
- 앱의 실제 발표 화면에 대한 smoke test 기록이 없다.
- 콜드 스타트와 반복 실행 latency가 없다.
- 메모리 사용량과 모델 캐시 크기가 측정되지 않았다.
- Hugging Face 10개 모델의 모든 출력값을 독립적으로 전수 검증하지 않았다.
- Solar의 `"."` 출력 원인은 확정되지 않았다.
- 사용자 수정분과 Solar 생성분을 행 단위로 완전히 분리한 provenance가 없다.
- 세션 시간은 관측 창일 뿐 순수 모델 처리 시간이 아니다.

따라서 이 사례를 Solar가 특정 Claude 모델보다 빠르거나 정확하다는 증거로 사용할 수 없다.

### 2026-07-23 재검증 업데이트

Task 03 후속 수정은 Ralphthon 경로와 공통 문서·Skill을 중심으로 진행됐으며, 감사 스냅샷에서 Task 04의 토크나이저 앱과 모델 자산 변경은 확인되지 않았다. 따라서 Task 04의 프로토타입·검증 정확성 판정은 그대로 유지한다.

다만 공통 작업 트리가 계속 변경 중이므로 저장소 전체의 최종 commit 준비 여부와 Task 04 진입 문서의 정합성까지 보장하는 의미는 아니다. Task 04 자체의 독립 oracle, UI smoke test와 latency 측정이 필요하다는 결론도 변하지 않는다.

## Claude를 대체할 수 있는가

이 태스크의 중심은 제품 요구를 작동하는 앱으로 만드는 코딩 업무다. Solar Open 2는 Claude Code 하네스 안에서 요구사항을 구조화하고, 모델을 조사하고, 다중 라이브러리를 연결해 Streamlit 앱과 검증 코드를 구현했으며 실행 과정의 문제도 디버깅했다. 따라서 유사한 내부 도구나 발표용 프로토타입의 **설계·코딩·통합·디버깅 범위에서는 Claude 모델을 대체해 투입할 수 있는 수준**을 보였다.

전문 비교 수치의 최종 보증은 별도 평가 축이다. 생성 모델이 누구든 구현 코드와 같은 가정을 공유하는 검증만으로는 오류를 놓칠 수 있으므로 공식 tokenizer나 독립 fixture를 oracle로 두는 것이 일반적인 엔지니어링 절차다. 이 보강 필요성을 앱 구현 능력 전체의 실패로 확대해석하지 않는다. 다만 동일 조건의 Claude 대조군이 없으므로 모델 간 동등성이나 우위까지 주장하지는 않는다.

실무 적용 판단은 다음처럼 구분하는 것이 적절하다.

| 역할 | 대체 가능성 | 조건 |
|---|---|---|
| 요구사항 분석과 앱 설계 | 높음 | 발표 목적을 단일 화면 구조로 구체화 |
| 프로토타입 구현 | 높음 | 다중 모델 비교 앱을 실제 코드로 완성 |
| 외부 라이브러리 통합·디버깅 | 높음 | 접근·로드·호환 문제에 반복 대응 |
| 발표 UI 구현 | 높음 | 실제 화면 smoke test를 더하면 운영 확인 가능 |
| 전문 비교값 산출 | 조건부 | 공식 tokenizer·oracle 대조 필요 |
| 최종 발표 데이터 보증 | 별도 검증 영역 | 사람 또는 독립 시스템의 확인 필요 |

결론적으로 Solar Open 2는 이 태스크에서 **프로토타입의 설계·코딩·통합·디버깅을 맡는 Claude 대체 모델로 활용할 수 있다.** 공식 토크나이저 기반 oracle 테스트를 추가하면 구현 성과를 발표 데이터까지 신뢰할 수 있는 도구로 확장할 수 있다.

## 최종 판정

Task 04의 최종 판정은 다음 네 문장으로 요약할 수 있다.

1. **요구사항 분석과 설계: 매우 양호** — 발표 목적과 비교 방식을 실제 앱 구조로 적절히 구체화했다.
2. **코딩·통합·디버깅: 양호** — 여러 모델을 연결하고 약 91분의 주 세션에서 실행 가능한 Streamlit 프로토타입을 완성했다.
3. **전문 수치 검증: 보강 필요** — GPT fallback 오계산과 Solar의 비정상 분할을 찾을 독립 oracle이 필요하다.
4. **Claude 대체 관점: 코딩 범위에서 대체 가능** — 동일 조건의 직접 비교는 없지만 유사한 프로토타입 구현 업무에 투입할 실질 역량을 보였다.

이 평가는 Task 03의 저장소 재편 성과와 분리한다. Task 03에서 파일이 잘 정리되고 커밋됐더라도 Task 04의 계산 정확성이 개선되는 것은 아니며, 반대로 Task 04의 검증 실패를 Task 03의 구조화 성능으로 감점해서도 안 된다.
